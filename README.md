# 채용 리포트 자동 생성 에이전트

기획 문서는 [PRD.md](PRD.md) 참고. 이 README는 "지금까지 만든 것 + 실행 방법"만 다룬다.

## 설계 원칙: 에이전트는 판단이 필요한 일만 한다

핵심지표/세부지표/연간누적지표는 전부 고정된 집계 쿼리라 판단이 필요 없다 — 그래서 LLM을 쓰지 않는
순수 함수(`generate_report_tabs.py`)가 DB에서 직접 계산하고, 웹앱의 `/metrics` 화면이 매 요청마다
다시 계산해서 표로 보여준다(외부 계정 불필요, Sheets는 선택 기능으로만 남겨둠). 에이전트가 하는 일은
"이번 기간에 뭐가 이상한지 판단 → 원인 조사 → 인사이트 작성"뿐이고, 그 결과물은 Sheets가 아니라
우리 앱 DB에 초안(draft)으로만 저장된다. 승인(발행) 권한 자체가 에이전트에게 없다.

## 지금까지 만든 것

- `app/db_schema.sql` — 원본 채용 데이터 SQLite 스키마 (PRD 3장)
- `app/generate_synthetic_data.py` — 24개월치(2024-09~2026-08) 합성 채용 데이터 생성기.
  실행하면 `data/recruiting.db`에 적재하고, 의도적으로 주입한 이상치 2건을
  `data/synthetic/anomaly_log.json`에 기록한다.
- `app/tools/query_recruiting_db.py` — **도구 1** (에이전트용): 읽기 전용 DB 조회
- `app/tools/run_chart_code.py` — **도구 2** (에이전트용): 관리도(Control Chart, μ±2σ) 기반 이상치 판단
- `app/tools/write_insight_draft.py` — **도구 3** (에이전트용): 우리 앱 DB(`insight_drafts`)에
  인사이트를 **항상 draft 상태로만** 기록. 승인 기능 자체가 없음
- `app/insight_store.py` — `insight_drafts` 테이블 접근. `save_draft()`(도구가 씀)와
  `approve()`(사람이 앱에서 승인 버튼을 눌렀을 때만 서버가 씀 — 에이전트 도구 아님)를 분리해둠
- `app/sheets_writer.py` + `app/generate_report_tabs.py` — **에이전트가 아닌 평범한 스크립트**.
  DB를 조회해서 Google Sheets의 kpi/detail/ytd 3개 탭을 매번 통째로 새로 씀 (Looker Studio가
  이 시트를 보고 대시보드를 그림)
- `tests/smoke_test.py` — 도구 3개를 실제로 이어붙여 파이프라인이 동작하는지 확인하는 스크립트
- `app/agent_loop.py` — **에이전트 루프** (OpenAI 함수 호출). 계획→도구호출→관찰→결정을 반복하고,
  재조회 5회/시간 3분 제한을 코드로 강제한다. 모든 단계를 `app/run_log_store.py`에 trace로 남긴다
- `app/web/` — FastAPI 웹앱. 대시보드(리포트 생성) / 실행 상세(로그+draft+승인) / 실행 이력(비용) /
  핵심지표(`/metrics`, 기간을 가로축으로 돌린 히트맵 표 — 세로 나열보다 추세가 한눈에 보이게)
- `eval/` — 평가 세트. `cases.py`(골든 케이스 6개: 주입한 이상치 2건 + 정상 기간 4건),
  `run_eval.py`(완료율/정답률/환각의심/비용을 표로 채점, 결과는 `eval/results/*.csv`)

## 실행 방법

```bash
python -m venv .venv
.venv\Scripts\activate        # Windows
pip install -r requirements.txt

# 1) 합성 데이터 생성 (data/recruiting.db 생성)
python -m app.generate_synthetic_data

# 2) 에이전트 도구 3개가 실제로 맞물리는지 확인 (조회 → 이상치판단 → DB에 draft 저장)
python -m tests.smoke_test

# 3) 숫자 탭(kpi/detail/ytd)을 Google Sheets에 채우기 — 에이전트 아님, 그냥 스크립트
python -m app.generate_report_tabs

# 4) 웹앱 실행 (http://localhost:8800) — .env에 OPENAI_API_KEY 필요
python -m uvicorn app.web.main:app --port 8800

# (4-1. CLI로 에이전트 1회만 실행하고 싶을 때)
python -m app.agent_loop 2026-03 2026-03

# 5) 평가 세트 실행 (기존 run 재사용, 없는 케이스만 새로 호출 — 과금은 신규 케이스만)
python -m eval.run_eval
```

`smoke_test.py`는 2025-04~2026-03 오퍼 수락률 시계열을 조회하고, 마지막 달(2026-03,
의도적으로 주입한 이상치)이 관리도 상 실제로 잡히는지 검증한 뒤, 결론을 DB에 draft로
저장하고 다시 읽어서 status가 draft인지 확인한다. 현재 통과 상태.

## Google Sheets 연동 (선택 사항 — 안 켜도 `/metrics` 화면으로 충분함)

기본적으로는 필요 없다. 숫자는 웹앱 `/metrics` 화면이 DB에서 바로 계산해서 보여준다(3.1 v0.5 참고).
그래도 Sheets에 내보내고 싶으면 `.env.example`을 `.env`로 복사한 뒤 아래 값을 채우면 로컬 폴백 대신
실제 Google Sheets에 쓰기 시작한다.

```
GOOGLE_SERVICE_ACCOUNT_JSON=<서비스 계정 키 json 파일 경로>
REPORT_SHEET_ID=<recruiting-report 스프레드시트 ID>
```

**스프레드시트는 1개, 탭은 3개**다 (승인 게이트가 필요한 판단 결과물이 여기 없으므로
staging/published를 나눌 이유가 없다):

| 코드상 이름(tab 파라미터) | 실제 시트 탭 이름 | 컬럼 헤더 |
|---|---|---|
| `kpi` | 핵심지표 | 기간, 총지원자, 자진포기, 불합격, 진행중 |
| `detail` | 세부지표 | 기간, 구분, 항목, 모집단구분, 값 |
| `ytd` | 연간누적지표 | 연도, 부서범위, 입사인원, 채용인원, 평균입사소요일, 평균채용소요일 |

`detail` 탭의 "구분" 컬럼 값은 퍼널/부서/채널/진행중비율 중 하나이고(코드상 category:
funnel/department/channel/in_progress), "모집단구분"은 채널 행에서만 전체지원자/합격자만
값이 들어가고 나머지 행은 빈 칸이다. Looker Studio 등으로 시각화하려면 이 한 탭을 "구분" 값으로
필터링해 퍼널/부서별/채널별/진행중비율 4개의 별도 차트로 나눠 그리면 된다.

인사이트(글)는 이 시트에 없다 — `insight_drafts` DB 테이블(3.2 참고)에 저장되고, 우리 앱의
리포트 미리보기 화면에서 `/metrics` 링크와 함께 보여준다.

## 실제 실행에서 발견하고 고친 버그 (2026-09-09)

실제 OpenAI 키로 에이전트를 돌려보면서 3가지 진짜 버그를 찾아 고쳤다 — 전부 "겉으로는 정상 종료됐는데
결과가 틀린" 케이스라 자동 테스트만으로는 못 잡았을 유형이다.

1. **기간 합산 버그**: 여러 달을 조회하면 `query_recruiting_db`가 몰래 다 더해서 하나의 숫자로
   돌려주고 있었다. 에이전트가 시계열을 만들려면 한 달씩 12번 조회해야 했는데 재조회 한도(5회)를
   넘어서 못 만들고, 이미 봤던 명백한 이상치(`offer_signed=0`)를 놓친 채 "특이사항 없음"으로 결론
   내렸다. → 여러 달 조회 시 달마다 한 행씩 나뉘어 돌아오도록 수정.
2. **날짜 형식 오류가 조용히 빈 결과로 처리됨**: 에이전트가 `2025-11-01`처럼 일(day)까지 넣으면
   문자열 비교상 필터에 안 걸려 빈 배열이 돌아왔다 — "데이터 없음"과 "형식 오류"가 구분이 안 됨.
   → 형식이 틀리면 명확한 에러 메시지로 막도록 수정 (에이전트가 바로 자가 수정하는 것 확인).
3. **웹앱 경쟁 상태(race condition)**: "리포트 생성" 버튼을 누르면 백그라운드 스레드가 실행을
   시작하기 전에 리다이렉트된 페이지가 먼저 도착해 404가 떴다(실행 자체는 백그라운드에서 계속 진행됨).
   → 스레드를 시작하기 전에 run 레코드를 먼저 동기적으로 만들도록 수정.
4. **분석은 다 해놓고 저장을 안 하고 끝남**: 에이전트가 원인 분석까지 텍스트로 길게 써놓고
   `write_insight_draft`를 호출하지 않은 채 응답을 끝낸 경우가 있었다(재조회 한도는 여유 있었음).
   루프가 "도구 호출이 없으면 끝난 것"으로 오판해서 `failed` 처리됨 — 사용자가 대시보드에서
   `2026-02~2026-04` 실행이 `failed`로 뜬 걸 보고 알려줌. → 도구 호출 없이 끝나려는데 아직
   저장 전이면, 포기하지 않고 "지금 바로 저장하라"고 최대 2번 다시 요구하도록 수정(`MAX_NUDGES`).
   재현 시나리오로 재실행해서 정상적으로 draft가 저장되는 것 확인함.

5. **핵심지표 화면이 세로 표라 추세가 안 보임**: 24개월치를 위아래로 나열한 표는 값이 어떻게
   변해왔는지 한눈에 안 들어온다는 피드백. → `app/web/pivot.py` 추가해서 기간을 가로축으로 돌리고
   값 크기에 따라 배경색을 칠하는 히트맵으로 변경(`app/web/templates/metrics.html`).

## 평가 세트 실행 결과 (2026-09-09, baseline, gpt-4o-mini)

`python -m eval.run_eval`로 골든 케이스 6개(이상치 2건 + 정상 4건) 실행. PRD 10.2절에 표 전체 있음.
요약: **완료율 6/6(100%), 정답률 4/6(67%), 총 비용 $0.0375**.

가장 중요한 발견은 **비결정성**이다 — 2026-03 이상치는 이전 수동 테스트에서 정확히 잡았는데 이번
평가 실행에서는 재조회 1번만 하고 "특이사항 없음"으로 결론 내렸다. 같은 입력에도 결과가 달라진다는
뜻이라 **단일 실행으로는 품질을 신뢰성 있게 측정할 수 없다** — 다음엔 케이스당 n회 반복 실행이 필요.
2025-11(채널 이상치)은 두 번의 독립 실행 모두 놓쳤다 — 이건 우연이 아니라 "퍼널부터 보고 끝내는"
전략적 편향으로 보임(위 "남은 관찰" 참고).
